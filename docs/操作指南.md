# 操作指南 — 在 DeepSeek Harness 中使用这套 LLM Wiki

> 配套文件：仓库规范 `AGENTS.md`、目录契约 `docs/目录结构说明.md`、全局索引 `index.md`、日志 `log.md`。
> 最后更新：2026-09-21

---

## 1. 两种会话入口与规范生效方式

| 入口                | 会话工作目录                         | AGENTS.md 生效情况                                                                             |
| ----------------- | ------------------------------ | ------------------------------------------------------------------------------------------ |
| 在 `<你的工作区根>` 启动 DSH | `<你的工作区根>`                       | 全局 `~/.dsh/AGENTS.md` 先加载，其中指定「涉及该仓库时必须遵守仓库内 AGENTS.md」；DSH 访问到仓库内文件后也会自动加载仓库级 `AGENTS.md` |
| 把工作目录设为仓库本身       | `<你的仓库绝对路径>` | 仓库级 `AGENTS.md` 是工作目录所在项目的规范，直接生效（最可靠）                                                     |

**建议**：做知识库相关工作时，在首条消息里显式声明目标，例如

> 按 `ObsidianVault for DSH/AGENTS.md` 的规范，Ingest 这篇论文：<链接>

这样既触发全局指针，也确保 Agent 完整读过仓库规范。

## 2. 指令范式速查

| 你想做的事       | 推荐指令                                                  | Agent 会做的事                                                                                    |
| ----------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **处理收件箱（最省事）** | **`处理收件箱`** | 扫描 `inbox/` → 识别元数据 → 定主题 → 归档进 `raw/<topic>/` → triage → 编译知识页 → 更新索引/导航/日志 → 跑自检 → 汇报 |
| 把外部文章/网页入库  | `Ingest 这篇文章：<URL>`                                   | 抓取 → 写 `raw/<topic>/` → triage → 编译 `wiki/<topic>/` → 更新 `index.md`、`log.md` → 跑 grounding 自检 |
| 把本地 PDF 入库  | `Ingest 这篇 PDF：D:\...\example-source.pdf`                        | 提取文本 → 逐行保真写入 raw → 编译知识页                                                                     |
| 只想看会识别成什么 | `处理收件箱，先给我看计划`                                        | 跑 `ingest_files.py --plan`，列出每个文件的标题/作者/推测主题，**不写任何文件**                                      |
| 一次整理多篇      | `Research 一下「管网示例指标」，把这些文献都入库`                        | 分角度检索（含反面证据）→ 选源入库；**编译必须串行**（index/log 是共享状态）                                                |
| 问已有知识       | `Query：我对示例领域韧性了解多少？`                                 | 读 `index.md` → 全文检索 wiki → 综合作答并给出引用；**不写文件**                                                 |
| 比较两篇        | `Query：比较 EXA 与示例属性研究对「韧性」的处理方式`                      | 综合两页并指出分歧                                                                                     |
| 归档一次问答      | `把这个答案归档到 wiki`                                       | 写 `wiki/<topic>/<主题>.md`（`type: archive`、无 Raw）→ 更新索引（Summary 前加 `[Archived]`）→ 记日志           |
| 体检知识库       | `Lint 一下 wiki`                                        | 索引一致性、失效链接、Raw 引用、See Also 自动修复；其余只报告                                                         |
| 只查证据保真      | `Lint 证据：检查 wiki/example-topic/ 下的数字` | 核对承重数字是否逐字见于 raw，报告疑点                                                                         |
| 只重建索引       | `同步一下 index.md`                                       | 跑 `tools/sync_index.py` 并汇报漂移                                                                 |
| 查看结构        | `展示这个仓库的目录结构与所有权`                                     | 输出契约树与边界说明                                                                                    |

### 措辞提示

- **「Ingest」= 写文件**；**「Query」= 只回答**。想只问不改，就用 Query 的说法。
- 想强制插件旧式行为时不要用这些词——插件的 Ingest 在 Obsidian 命令面板里，不在 DSH 里。
- 不确定 Agent 会走哪条路时，直接说「只回答，不要写文件」或「请写入 wiki」。

## 3. 日常工作流

### 3.0 收件箱流程（推荐：日常就用这一条）

**这是设计给你的默认入口。** 两步，不需要整理、改名、分类：

**第一步 —— 丢文件**

把 PDF / Markdown / 文本 / HTML 直接复制进：

```
<你的仓库>\inbox\
```

不需要建子目录、不需要改文件名、不需要管主题。（浏览器/Zotero 导出的嵌套目录会被自动摊平；
`.crdownload` 这类未下载完的文件会被忽略。）

**第二步 —— 说一句话**

```text
处理收件箱
```

然后我会：扫描 → 识别元数据 → **判断主题** → 归档进 `raw/<主题>/` → 对照 wiki 做 triage →
编译知识页 → 更新索引与导航页 → 记日志 → 跑证据保真自检 → 向你汇报。

**验收信号：收件箱空了 = 全部处理完了。** 如果我说处理完了但收件箱还有文件，那就是有文件被跳过
（类型不支持 / 读取失败 / 没下载完），我会说明原因。

**想先看看会识别成什么**（不写任何文件）：

```text
处理收件箱，先给我看计划
```

我会列出每个文件的识别标题、作者、类型和**推测**主题。主题只是推测——最终归属由我按知识库现状判断，
也可能问你一句「这批算是示例检测主题还是并入韧性主题？」

### 3.1 单篇素材入库（临时用）

```text
Ingest 这篇：https://example.com/some-paper
```

期望输出：一份 raw 素材路径、triage 结论（New/Update/Disputed/No material）、新建或更新的知识页、
`index.md` 与 `log.md` 的变更、grounding 自检结果。

**验收自己的三件事**：raw 有没有元数据头？知识页 `Raw:` 行的链接能不能点开？`log.md` 里有没有对应条目？

### 3.2 批量整理一个主题

```text
先 Query 一下我对「示例领域韧性」的现有了解，再把 <你的素材目录> 下的这几篇 PDF 逐篇 Ingest，
遇到与已有页面冲突的地方标 Status: Disputed，最后 Lint 一遍。
```

这样一条指令就能串起 **Query → Ingest × N → Lint**，也是本仓库最省事的「喂料」方式。

### 3.3 写作前的知识盘点

```text
Query：把 wiki 里关于「相对指标与可靠性的关系」的内容整理成一份对比，标注每条的出处。
```

### 3.4 定期体检

```text
Lint 一下 wiki，跑证据保真检查，并同步索引。
```

建议每周或每积累 5–10 篇素材后做一次。

## 4. 插件 UI 与 Agent 的分工（何时切回 Obsidian）

| 场景 | 用哪里 | 具体入口 |
|---|---|---|
| 把仓库里散落、格式不规范的 Obsidian 笔记变成实体/概念页并自动织 `[[链接]]` | Obsidian 插件 | 命令面板 → `Karpathy LLM Wiki: Ingest multiple files` / `Ingest from folder` |
| 在 Obsidian 里对wiki提问、看图谱 | Obsidian 插件 | `Query Wiki` 侧栏面板 / 原生 Graph View |
| 快速修死链、孤儿页、重复页 | Obsidian 插件 | `Karpathy LLM Wiki: Lint wiki` |
| 看每次摄取的产出 | Obsidian 插件 | `View Ingestion History` |
| 外部素材（URL/PDF/粘贴文本）的保真入库与长文编译 | DSH Agent | 本文第 2 节的 Ingest 指令 |
| 跨素材综合、比较、批判性梳理 | DSH Agent | Query / Research |
| 索引、日志、目录契约的维护 | DSH Agent | 自动完成 |

**插件侧状态：已就绪 ✅**（2026-09-21 14:20 核实）

| 项 | 值 |
|---|---|
| provider | `deepseek` |
| model | 你选的 model（可选列表：你选的 model、`deepseek-v4-pro`） |
| baseUrl | 你的 baseUrl |
| wikiLanguage | `zh` |
| `llmReady` | **true** |

上面的插件 UI 操作现在**全部可用**。随时复核：

```powershell
python tools/check_plugin_ready.py                  # 按插件源码逻辑复算 llmReady
python tools/check_plugin_ready.py --diff           # 再看插件有没有动过文件（对比快照）
python tools/sync_index.py --bridge-index --check    # 复核编译页是否仍登记在插件索引里
python tools/audit_vault.py                          # 全库体检（只报告不改文件，退出码恒 0）
```

`audit_vault.py` 是**横向体检**，补前面几个脚本的盲区：孤儿页、frontmatter 缺 `aliases`/
`summary`、`updated` 两处不一致、空目标 wiki-link、文档里对已删文件的过期引用、
以及「`tools/` 里有脚本但 `AGENTS.md` 工具表没登记」。它**不会**改任何文件，
退出码**永远是 0**——看到 `BUG` / `WARN` 计数后自己判断，别把它当成必须通过的红灯。
真正的硬闸门只有 `lint_grounding.py`（畸形 wiki-link 时退出码 1）。

### 让插件 Query 也能答编译知识（已启用）

插件的检索链路是 **`wiki/index.md` → 页面图 → 页面内容**；索引里没有的页面它一律不读
（源码 `main.js:79003`）。所以 `sync_index.py --bridge-index` 会把编译页按插件自己的 bullet 格式
登记进 `wiki/index.md` 末尾的 `<!-- AGENT-INDEX-START -->` 段：

```
- [[wiki/example-topic/示例页面 A|示例页面 A]] - 以应力—应变曲线评估韧性：…
```

于是插件 Query 面板也能检索到那 4 篇编译长文。

> ⚠️ **每次用插件 UI 摄取后必须重跑一次**：插件重建 `wiki/index.md` 是**整文件覆盖**
> （`generateFlatIndex` → `createOrUpdateFile` → `vault.process`），会把你这登记段整段抹掉。
> 所以标准流程是：**插件 ingest → `python tools/sync_index.py --bridge-index`**。
> `--check` 用来检测是否被抹（报 drifted 即被抹），可放进 Lint 流程。
> 被抹掉的只是索引里的一行登记，编译页与 `raw/` 完全不受影响。

注意：仓库根的 `LLM Wiki 导航.md` 与 `index.md` **只有 Obsidian 与 DSH 能用**，
插件 Query 读不到（它只读 `wiki/index.md`）。

`--diff` 是验证双轨隔离是否成立的手段：用插件 UI 摄取一篇笔记跑一次，再 `--diff`，
就能看到它只新增了 `entities/`、`concepts/`、`sources/`，而没有碰你的 `wiki/<topic>/`。

注意：`wiki/Welcome to Karpathy LLM Wiki.md` 里可能残留 `LLM client not configured` 字样——
那是首次运行（LLM 未配置时）生成的英文笔记，插件不会自动重写它。它不影响功能；
想让内容刷新，用命令面板的 `Karpathy LLM Wiki: Recreate Wiki Welcome Note`。

## 5. 常见问题

**Q：为什么 Obsidian 的 Query Wiki 搜不到我刚编译的文章？**
A：插件的检索入口是 `wiki/index.md`（只列出 `entities/concepts/sources`）与它自己维护的链接图，
而 Agent 编译的长文在 `wiki/<topic>/`，是刻意隔离的。要问这些内容，用 DSH 的 Query。

**Q：我在 Obsidian 里手动改了 `wiki/index.md`，会不会有问题？**
A：会被覆盖。插件每次重建索引都是**整文件覆盖**（`vault.process`），你手写的内容会消失；
它末尾那段 `<!-- AGENT-INDEX-START -->` 也是靠 `sync_index.py --bridge-index` 重新写入的。
所以要改人的目录，改仓库根的 `index.md`；要恢复插件索引里的编译页登记，重跑 `--bridge-index`。

**Q：Agent 写的页面会被插件删掉吗？**
A：不会。插件的 Lint 只处理 `wiki/{entities,concepts,sources,schema,contradictions}` 范围。若仍想加保险，
可在页面 frontmatter 加 `reviewed: true`（插件对所有写入者都跳过该页）。

**Q：`index.md` 没跟上新增页面怎么办？**
A：`同步一下 index.md`，或让 Agent 跑 `python tools/sync_index.py --check` 看漂移。

**Q：怎么判断知识页有没有瞎编数字？**
A：让 Agent `Lint 证据`，或自己跑
`python tools/lint_grounding.py`。它会抽出页面里的百分比、小数、日期、金额，逐一核对该页 `Raw:` 链接的原文。

**Q：能不能既有插件的图谱，又有 Agent 的编译页？**
A：可以，两者现在就在同一个 vault 里共存。Obsidian 的 Graph View 会同时显示两类页面；
Agent 页面之间的 `[[wiki-link]]` 也会成为图的边。

**Q：PDF 怎么进去的？**
A：把 PDF 丢进 `inbox/` 然后说「处理收件箱」，或直接 `Ingest 这篇 PDF：<路径>`。
实际执行的是 `tools/ingest_files.py`：它读 PDF 元数据、生成 `<年>-<作者姓>-<slug>` 文件名、
**逐行保真**把文本层搬进 `raw/<topic>/*.md`（只把页码标记转成 HTML 注释，不改写任何措辞），
原始 PDF 同时归档到 `raw/<topic>/pdfs/`。

**Q：以前那些临时脚本还在吗？**
A：不在。`build_raw_from_pdfs.py`（首批 4 篇的一次性脚本）与 `ingest_pdfs.py`（被 `ingest_files.py` 取代）
都已删除。**每次删除都记在 [`更新公告.md`](../更新公告.md) 的「本次会话已删除的文件」清单里**，
并写明删除原因与替代方案——想找旧脚本的行为，看那里。
